● Li o build_portable.py (530 linhas) e os scripts de apoio. Rodei só python 
  build_portable.py check, que acusou os problemas abaixo. Não rodei qa nem
  build, porque são longos e escrevem em dist/.

  O que ele faz
  - python build_portable.py executa as verificações de qualidade (fmt, clippy 
    -D warnings, test, build release), compila o neoveg_ui para cada alvo e
    monta o pacote em dist/.
  - Para cada alvo ele gera a pasta Neoveg-Portable-<rid>/, o zip (Windows) ou
    tar.gz (Linux e macOS) e o executável avulso.
  - No Windows o executável avulso usa o runtime C estático, então não precisa
    do redistribuível do Visual C++.
  - Ele também grava SHA256SUMS.txt, build_manifest.json e o relatório de QA,
    que o docs/index.html lê.
  - O Docker (docker/entrypoints/build-*.sh) reaproveita o mesmo script para
    Linux e macOS. O --sync espelha para o Google Drive.
  - A estrutura bate com o que o AGENTS.md descreve. É Python só com biblioteca
    padrão e não há cópia de arquivos legados no pacote.

  Problemas encontrados
  1. check dá falso erro neste PC. A toolchain do Rust está em C:\Program 
     Files\Rust stable MSVC 1.99 e não usa rustup. O check marca rustup, clippy
     e rustfmt como FAIL, embora o clippy funcione normalmente. O qa e o build
     não dependem disso. Para alvos de outro sistema, installed_targets() volta
     vazio e o build manda rodar rustup target add, o que não resolve aqui. A
     correção é testar cargo clippy --version e cargo fmt --version em vez de
     consultar o rustup.
  2. O CI do GitHub é o modelo antigo do .NET.
     .github/workflows/dotnet-desktop.yml ainda tem os placeholders
     your-solution-name e Wap_Project_Path, e roda dotnet test e msbuild. Ele
     deve falhar em todo push ou PR para main, e não valida o Rust. É o item
     "CI" aberto no roadmap. Não rodei o workflow para confirmar.
  3. O dist/ está cheio de resíduos do C#. A pasta tem o Neoveg.exe de 280 MB,
     desktop-host, cpp-extensions, runtimes e um AppDir antigo. O
     build_manifest.json atual é da era .NET. O stage_package apaga a pasta do
     alvo antes de remontar, mas só a do alvo que você construir. Os alvos que
     você não construir (por exemplo osx-x64) continuam com o lixo antigo. O
     dist/ está no .gitignore, então é só limpeza local.
  4. A raiz do repositório está poluída por legados (Neoveg.exe, Avalonia*.dll,
     neoveg_core.dll e outros). Eles estão no .gitignore e não entram no pacote,
     porque o script copia só a lista PAYLOAD_FILES e os JSON de i18n. É o item
     "remover diretórios legados".
  5. Os JSON de i18n vão como Assets/i18n, mas a pasta de origem é assets/i18n 
     em minúsculas. No Windows e no Mac isso não importa. No Linux, que
     diferencia maiúsculas, assets existe como está, então copia. Só convém
     conferir se o app procura Assets/i18n e se o git guarda o nome certo.
  6. Com --ffmpeg, o executável avulso sai sem as DLLs do FFmpeg. Só o pacote
     portátil as leva. Isso não está documentado. No macOS elas não são
     copiadas, e o script apenas avisa.
  7. O build compila duas vezes. O passo de QA faz cargo build --workspace 
     --release e depois o cargo_build refaz o do neoveg_ui, com RUSTFLAGS
     diferente no Windows (crt-static). Isso invalida o cache e a compilação
     inteira se repete. Seria mais rápido tirar o build do workspace do QA ou
     compilar com os mesmos flags.

  Quer que eu corrija o check (item 1) e troque o workflow do CI por um de Rust
  (item 2)? Esses dois são os de maior impacto. Os itens 3 e 4 são limpeza local
  e não mexi neles.
